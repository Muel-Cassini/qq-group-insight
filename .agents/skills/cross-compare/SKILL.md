# 群聊 × 社媒 交叉比对与二次总结

输入两侧产物，输出**比对材料**（`compare.md` / `compare.json`），再由你撰写最终总结。
比对脚本纯本地文本处理，不联网、不调用外部命令。

> 面向人的操作手册在 `GUIDE.md`（参数表、输出说明、调参与故障对照）；主题词表与打分阈值在 `config.json`，脚本每次运行自动读取，无需改代码。

## 一、前置产物

| 来源 | 由谁产出 | 脚本需要的内容 |
|---|---|---|
| 群聊 | `qq-group-summary` 技能 | 输出目录中的 `normalized.jsonl` |
| 社媒 | `social-crawl` 技能 | 输出目录中的 `*.jsonl`（contents 与 comments） |

两侧都要有非空数据；缺失时脚本会返回 `ok:false` 并提示是哪一侧为空。

## 二、执行比对

```powershell
python .agents/skills/cross-compare/scripts/compare.py `
  --qq     "artifacts/qq/<群名>-<区间>" `
  --social "artifacts/social/<本次采集目录>" `
  --out    "artifacts/compare/<日期>"
```

| 参数 | 说明 |
|---|---|
| `--top` | 最多输出多少组配对（默认 40） |
| `--min-score` | 配对最低相似度阈值（默认 0.18，材料太少就调低到 0.12） |
| `--max-qq` | 只取最近 N 条群聊消息（群消息很多时用它聚焦近期） |

## 三、输出怎么读

`compare.md` 的五个部分：

1. **共同主题** —— 两边都在讨论的领域词（含提及次数），这是最值得写的交叉点（也是互证点：群里讨论的，社媒上是否有印证）。
2. **高相关配对** —— 群聊消息 ↔ 社媒内容的相似度配对，带共同词、共同主题、社媒高相关评论。相似度只代表「话题接近」，**不代表观点一致**，必须自己读内容判断是印证、补充还是冲突。
3. **主题明细** —— 每个共同主题下两侧的代表性材料（群聊取最近 3 条、社媒取互动量最高 3 篇）。
4. **单边主题** —— 只在群里聊、社媒没有的（可能是群内私有经验或过时信息）；只在社媒火、群里没提的（可能是信息差）。
5. **时效性** —— 社媒内容相对群聊时间的先后分布，用来判断「群里的说法是否已被更新的信息覆盖」（`social_newer_Nd` 越多，越要提示信息更新）。

## 四、二次总结的写作要求

1. 先读 `compare.md`，再按需回到 `normalized.jsonl` 与社媒 jsonl 核对原文；**不要只看摘要就下结论**。
2. 每条结论必须标注证据来源：群聊写「群名 日期 时间 发送人」，社媒写「标题 + 链接 + 作者/互动量」。
3. 明确区分三类结论：
   - **互证**：群聊与社媒说法一致；
   - **补充**：社媒提供了群里没有的做法/数据（注明时间，越新越优先）；
   - **冲突/存疑**：两边说法矛盾，或社媒内容明显早于群内讨论而可能过时——这类要标「需核实」，不要替用户拍板。
4. 输出结构建议：① 一句话结论 ② 交叉印证的关键结论（带证据）③ 群聊盲区（社媒有、群里没有）④ 群聊私有价值（社媒没有的群内经验）⑤ 冲突与待核实清单 ⑥ 建议的下一步动作。
5. 相似度低但语义相关的配对（例如群里说「容器重启」、社媒说「OOMKilled」）要靠你的理解补上；`compare.json` 里的 `shared_terms` / `shared_topics` 只是线索。
6. 结论里不要出现「根据爬取的数据」这类空话，直接给内容；数字要具体（多少条消息、多少篇笔记、互动量多少）。

## 五、红线

- 不把两侧原始数据（尤其含个人信息、私聊内容、cookie）写进总结正文；需要引用时脱敏。
- 不因为社媒声量大就把「高赞但无依据」的说法写成结论——互动量只做权重参考。
- 总结只写在工作区 `artifacts/compare/` 下，不改动上游产物。
